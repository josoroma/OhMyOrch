# CLAUDE.md — OhMyOrch Harness Project Contract

This file is the top-level contract for any Claude Code session working in this
repository. It is loaded automatically. Read it before acting.

## What this repository is

This repository is the **OhMyOrch Harness**: a reusable, spec-driven multi-agent
delivery workflow for Claude Code plus OpenSpec.

It is a **documentation- and configuration-first project**. There is no
application runtime, package manifest, or build. The deliverables are Markdown
contracts, the harness's own agent, skill, and rule definitions, and the portable
bash scripts under `scripts/` that enforce them (with their own regression suites).

## Document map

Product documents live at the repository root in this repository. Every harness
script resolves both `docs/<file>` and the repository root, so a host repository
may use either layout unchanged — prefer whichever it already uses.

| File | Role | Normative? |
|---|---|---|
| `PRD.md` | Product intent for the harness itself | Yes — for intent |
| `SPECS.md` | Iterable implementation backlog (epics, stories, acceptance criteria) | Yes — for scope |
| `CODEBASE.md` | Current-state map of an analyzed repository (absent here: greenfield) | No — descriptive evidence only |
| `README.md` | Operational handbook: install, ingest, deliver, resume, tooling | No — explanatory |
| `SPEC-LOGS/README-EPIC-N.md` | Per-epic delivery records | No — explanatory |
| `CLAUDE.md` | This contract | Yes — for session behavior |
| `openspec/specs/` | Canonical capability specs, synced from archived changes | Yes — for current behavior |
| `openspec/changes/archive/` | One archived change per delivered story (full artifact trail) | Yes — for change history |
| `docs/pages/` | Themed single-page HTML generated by `/generate-html-page` | No — explanatory |
| `openspec/delivery/goal.md` | The recorded delivery goal (`/deliver`); derived by `scripts/delivery.sh` | No — derived record |
| `.claude/` | Agents, skills, rules, settings | Yes — for role behavior |
| `scripts/` | The executable harness: validators, guards, reporters, suites | Yes — for enforcement |
| `docs/resets/` | Timestamped backups written by `/harness-reset` | No — recovery snapshots |

## Authority order

When sources disagree, resolve in this order:

```text
1. Explicit human Product Manager decision
2. Approved product source documents (PRD.md, source material)
3. Existing PRD.md (when updating)
4. CODEBASE.md — descriptive current-state evidence, never intent
```

`CODEBASE.md` may constrain feasibility, reveal compatibility requirements, and
document what already exists. It **MUST NOT** silently become the desired
product requirement.

## Workflow

```text
SPECS.md READY story
   -> /opsx:explore     understand problem + repository (no implementation)
   -> /opsx:propose     proposal.md, delta specs, design.md, tasks.md
   -> implementation-plan.md   (Planner handoff)
   -> /opsx:apply       implement approved tasks
   -> review.md         (Reviewer findings)
   -> /opsx:verify      verify implementation against specification
   -> test-report.md    (Tester acceptance evidence)
   -> /opsx:archive     archive change, update canonical specs
   -> SPECS.md story marked DONE
```

Deliver **one bounded change at a time**. `SPECS.md` is a backlog, not a single
implementation prompt.

### Goal-driven delivery

`/deliver <EPIC-N | US-N.M | US-N.M#k | "task text">` (skill `.claude/skills/deliver/`)
runs the workflow above as a loop. It delivers each story of the target as its own
change, in `SPECS.md` order. The next action is always derived by
`scripts/delivery.sh next`, never remembered. Each action is delegated to its owning
role. `scripts/guard-delivery-loop.sh`, wired as a `Stop` hook, keeps the session
working while the goal is `ACTIVE`. It allows the stop only when the goal is
`COMPLETE`, or `BLOCKED` by an escalation or lack of progress. The orchestrator never
authors `review.md` or `test-report.md`, and the loop has no gate exceptions. Rules:
`.claude/rules/delivery-loop.md`.

## Hard rules

1. **No silent product assumptions.** Never invent externally observable
   product behavior. Missing or contradictory behavior becomes
   `NEEDS CLARIFICATION` or `BLOCKED`, not a fabricated requirement.
2. **Separation of duties.** The agent that implements a change must not be the
   authority that approves its implementation or acceptance result. The
   Implementer never authors `review.md`.
3. **One manageable change.** Do not collapse multiple independently verifiable
   stories into one project-sized OpenSpec change.
4. **Repository artifacts are durable state.** Persist workflow state in files
   so a fresh session can resume without hidden chat history.
5. **Acceptance is mandatory.** A story must not be `READY` unless its expected
   observable behavior is testable.
6. **Context before generation.** When `CODEBASE.md` exists, any workflow that
   creates or materially updates `PRD.md` or `SPECS.md` must read it first.
7. **Reviewers and testers do not repair.** The Reviewer must not silently fix
   reviewed product code; the Tester must not silently repair failing behavior.
   Both return findings to the Implementer.

These rules are expanded, with their mechanical enforcement, in `.claude/rules/`
(see the index in `.claude/rules/README.md`). Where a rule and an agent prompt
disagree, the rule governs.

## Agent roles

| Role | Responsibility | May edit product code? |
|---|---|---:|
| Codebase Analyst | Inspect a repository, create/refresh `CODEBASE.md` | No |
| Product Specifier | Generate/update `PRD.md` | No |
| Spec Ingestor | Generate/update `SPECS.md` | No |
| Product Manager | Select work, orchestrate, control gates, archive | No by default |
| Planner | Explore repository, produce `implementation-plan.md` | No |
| Implementer | Implement the approved change and its tests | Yes |
| Reviewer | Verify against specification, write `review.md` | No |
| Tester | Validate acceptance criteria, write `test-report.md` | No |

The human Product Manager remains the final product authority.

## Working in this repository

- Preferred editors: `replace_string_in_file` for edits; `create_file` for new files.
- There is no application test runner. Validate changes by running the harness
  suites and validators, which must all pass:

  ```bash
  scripts/test-write-scope.sh && scripts/test-guards.sh \
    && scripts/test-status.sh && scripts/test-completion.sh \
    && scripts/test-delivery.sh && scripts/test-html-page.sh \
    && scripts/test-harness-reset.sh
  node scripts/check-frontmatter.js
  scripts/validate-product-artifacts.sh
  openspec validate --all --strict
  ```
- New harness contracts are Markdown. Keep them concise, imperative, and
  testable.
- `/harness-reset` returns the repository to the canonical initial state. It backs
  the scoped artifacts up to `docs/resets/<timestamp>/` first and verifies the
  backup before changing anything; `.claude/` is never written. Run
  `scripts/harness-reset.sh --dry-run` to see the plan without changing anything.
- Do not commit `.claude/settings.local.json`; it holds machine-local secrets.
  Track `.claude/settings.json` instead.
- OpenSpec's generated `.claude/commands/opsx/` and `.claude/skills/openspec-*`
  files are managed by the OpenSpec CLI. Regenerate with `openspec update`
  rather than hand-editing where possible.

## Status vocabulary

User stories and workflow states use exactly these values:

```text
Story:  READY | NEEDS CLARIFICATION | BLOCKED | IN PROGRESS | DONE
Change: PROJECT_DISCOVERY | CODEBASE_ANALYSIS | CODEBASE_READY | SOURCE_DOCUMENTS
        | PRD_GENERATION | PRD_READY | SPEC_INGESTION | SPECS_READY | SELECTED
        | EXPLORING | PROPOSED | PLANNED | IMPLEMENTING | REVIEWING
        | CHANGES_REQUESTED | TESTING | TEST_FAILED | ACCEPTED | ARCHIVED | BLOCKED
```

Full state model: `PRD.md` section 12.
