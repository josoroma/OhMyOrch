## Test Strategy

There is no application test runner. The Implementer's checks are
`scripts/test-html-page.sh` plus the full harness chain. The Tester repeats them
independently. **Two clauses cannot be shown by static checks and need a browser:**
Scenario 2's runtime behaviour (§B) and Scenario 4's "a reader inspects it" (§D, visual
rendering). The Tester can use the integrated browser against the `file://` page, or
score those clauses `UNVERIFIED`. The static rules are necessary evidence but not proof
of runtime behaviour.

**Page flattening (shared by every rule).** Read the page once into a variable, or a temp
file under `mktemp -d`, with newlines and tabs translated to spaces
(`tr '\n\t' '  ' < "$PAGE"`). Tags, `<svg …>` attributes, and CSS rules can span lines, so
line-oriented `grep` misses them. Match tags with `grep -oiE '<svg[^>]*>'` and similar on
the flattened text.

**§A — Scenario 1: tokens (tasks 1.2, 1.4, 2.1). The BSD-awk approach, verified on this
machine** (`awk version 20200816`, `GNU bash 3.2.57`) in a throwaway `mktemp -d` directory:

1. Extract the `<style>` bodies:
   `awk '/<style[^>]*>/{f=1; sub(/.*<style[^>]*>/,"")} /<\/style>/{sub(/<\/style>.*/,""); print; f=0} f'`.
2. Flatten: `tr '\n\t' '  '`.
3. Strip CSS comments **before** splitting into rules, using an `index()` loop over `/*` …
   `*/`. The probe confirmed that a `}` inside a comment otherwise ends the record early,
   and `:root` came back empty.
4. Split into rules with `awk 'BEGIN{RS="}"}'`. In each record, the selector is the text
   before the first `{`, trimmed. Accept a record only when the selector string equals `:root`
   (or `.dark`). Compare with `==`, not a regex: a regex treats `.` as any character, and
   `.dark .card { … }` or `@media (…) { .dark` must not match.
5. Split the body on `;`. Split each declaration at the **first** `:` with
   `index()`/`substr()`, because values contain `:`-free but `/`- and `%`-bearing text. Trim
   the name and value, and collapse runs of spaces in the value to one. Emit `--name: value`.
6. For each expected line from the validator's heredoc, check it with
   `grep -qxF -- "$line"` against the extracted set. `-F` makes `/`, `%`, `(`, `.` literal;
   `-x` forces a whole-line match; `--` protects the leading `--`. On a miss, report the
   found value, which you look up with `awk -F': ' -v n="$name" '$1==n{v=substr($0,length(n)+3)} END{print v}'`
   (the last occurrence wins, mirroring the CSS cascade).

The probe's output for a page containing `:root{--radius:0.625rem;--background:oklch(1 0 0);`,
`--border:   oklch(0.922  0 0) ;}`, a `/* palette } tricky */` comment, an `@media` block, a
`.dark .card` rule, and a `.dark` block holding `--border: oklch(1 0 0 / 10%);`:

```text
--root
--radius: 0.625rem
--background: oklch(1 0 0)
--border: oklch(0.922 0 0)
--dark
--background: oklch(0.145 0 0)
--border: oklch(1 0 0 / 10%)
fixed-string match OK
```

Portability rules the Implementer must keep:

- **Never pass a value through a `printf` format or a `sed s///`.** `%` in `10%` is a
  `printf` directive, and `/` is the `sed` delimiter. Use `printf '%s\n' "$v"`, `grep -F`, and
  awk `index()`/`substr()`.
- Do not use `awk -v` to pass values containing backslashes (the tokens have none; note it
  anyway).
- No `\|`, `\?`, `\{m,n\}` in BSD `sed` BREs (repo memory: they silently match nothing or
  eat the capture). Use `grep -E` or awk.
- No `mapfile`, associative arrays, or `${v^^}` (bash 3.2).
- Whitespace normalisation means `oklch(0.922  0 0)` equals `oklch(0.922 0 0)`. It does
  **not** treat `oklch(1 0 0/10%)` as equal to `oklch(1 0 0 / 10%)`. The contract is the
  supplied text, so a respaced slash fails.

Suite cases (task 2.1): `valid/page.html` passes; the template passes with `--no-sources`;
`invalid/tokens-light.html` (one light value altered) → exit 1 and `tokens-light`;
`invalid/tokens-dark.html` (one dark token removed) → exit 1 and `tokens-dark`;
`invalid/tokens-dark-scoped.html` (dark tokens only under `.dark .card`) → `tokens-dark`;
a page with extra spaces inside values passes; the slash-and-percent value passes when
written as supplied. Add a template-sync case that runs the validator on
`scripts/templates/html-page.html` so the template and the heredoc cannot drift.

**§B — Scenario 2: the toggle (tasks 1.2, 1.4, 2.2).** The static `toggle` rule requires all
of the following:

- a control with a stable hook: `id="theme-toggle"` (recommended);
- `classList.toggle("dark"` or `classList.toggle('dark'`, or an add/remove pair, applied
  to `document.documentElement`;
- `localStorage`;
- `prefers-color-scheme` (the `matchMedia` call).

Suite cases: one `invalid/toggle-*.html` per missing element → exit 1 and `toggle`.
**Runtime (Tester):** open the page from `file://` and check four things: click → `<html>`
gains or loses `class="dark"`; reload → the choice holds; clear storage and emulate
`prefers-color-scheme: dark` → the page starts dark. Wrap `localStorage` in `try/catch` so a
browser that blocks storage on `file://` still renders.

**§C — Scenario 3: TOC (tasks 1.1, 1.4, 2.3).**

- `toc`: on the flattened page, find the byte offset of the first `<nav[^>]*class="[^"]*toc`
  and of the first `<section` with awk `match()`. Fail when the nav is missing or its offset
  is greater.
- Extract the nav block (from `<nav` to the first `</nav>` after it), and from it the
  `href="#…"` targets. Extract every section id: `grep -oiE '<section[^>]*>'`, then pull
  `id="…"` from each; attribute order is free, so do not assume `id` comes first. Fail
  `toc` for each section id not in the nav targets.
- `toc-links`: collect every `href="#…"` on the page, and every element id with
  `grep -oE '[[:space:]]id="[^"]*"'`. The leading `[[:space:]]` keeps `data-id=` and
  `aria-labelledby=` from matching. Fail for each target with no id. Treat an empty
  fragment (`href="#"`) as unresolved; the template uses a `<button>` for the toggle, so
  it needs none.

Verified on the probe page: `href` targets `a`, `missing`; ids `a`, `t1`.
Suite cases: `invalid/toc-after-section.html`, `invalid/toc-unlinked-section.html` → `toc`;
`invalid/toc-links-dangling.html` → `toc-links`.

**§D — Scenario 4: components (tasks 1.3, 2.4).**

- The template carries `data-component="table"`, `"list"`, `"diagram-overlay"`,

**§E — Scenario 5: self-contained (tasks 1.4, 2.5).** All matches are case-insensitive
(`grep -iE`) on the flattened page:

- `<script[^>]*[[:space:]]src=`
- `<link[^>]*rel=["']?stylesheet`
- `@import`, and `url\(["']?(https?:)?//` (this covers protocol-relative `//cdn`)
- `@font-face` whose body contains a remote `url(`

To avoid a false positive on a page that *explains* the rule, scan `@import`/`url(` only
inside `<style>` bodies and `style="…"` attributes, and scan tags only as raw `<…>`. Escaped
text (`&lt;script src&gt;`) must pass. Suite cases: one fixture per vector
(`self-contained-script.html`, `-link.html`, `-import.html`, `-url.html`, `-font.html`,
`-protocol-relative.html`, `-uppercase.html`) → exit 1 and `self-contained`, plus one
passing page that mentions `&lt;script src&gt;` in text.

## Open Questions

1. **Blocking: where are the supplied Luma tokens recorded?** `design.md` §3 and
   `proposal.md` say the palette was supplied, but no token name or value is in any
   repository file. The Product Manager must record the `:root` and `.dark` blocks as
   supplied, for example as a "Luma tokens" appendix to this change's `design.md` (via
   `/opsx:update`) or in a source document cited by `SPECS.md` US-14.1 `Source:`. That
   must happen before tasks 1.2 and 1.4's token rules, the token fixtures, and task 1.5
   can finish. The Planner has not guessed them, and the Implementer must not. Related
   sub-questions the recorded palette will answer: (a) does it include `--radius` and the
   `--sidebar-*` and `--chart-1..5` tokens; (b) does it include a Tailwind `@theme inline`
   block, which is not plain CSS and would be dropped from a single-file page; (c) may a page
   define tokens beyond the palette? The plan assumes extras are allowed and only the
   supplied set is checked.
2. **Toggle control hook.** The plan assumes `id="theme-toggle"` as the stable marker the
   `toggle` rule looks for. The scenario requires a toggle, not a name; this is a design
   detail the Implementer may settle, but it becomes part of the validator's contract once
   published.
3. **Task 1.6 has no genuine acceptance criterion.** Its `tasks.md` mapping to "The page
   presents content through the supported components" is nominal: allow-list entries and
   documentation make no scenario observable. It is necessary (the story's Tasks list
   requires the docs; `CLAUDE.md` requires suites to be in the validation chain), so the
   plan keeps it as a supporting task rather than inventing a criterion. Confirm that is
   acceptable, or add a documentation scenario to the story.
4. **`sources` rule strength.** `design.md`'s rule table says "a `section#sources` exists".
   The plan recommends also requiring at least one `<li>` or `<code>` inside it, because the
   scenario says the section is "listing the files and commands". This follows the scenario
   wording and does not add behaviour, but it is stricter than the design table. Confirm, or
   keep presence-only.
5. **`SPEC-LOGS/README-EPIC-14.md`.** Every other epic has a delivery record, but this
   change's Impact list does not name one. The plan leaves it out of scope.
