# OhMyOrch maintainer instructions

This repository authors the reusable Claude Code plugin at `plugins/ohmyorch/`. The root `.claude-plugin/marketplace.json` is the colocated catalog. Installed generic skills, agents, hooks and runtime code belong to the plugin; do not recreate executable copies under a consumer's `.claude/` or `scripts/`.

Start local authoring sessions with `claude --plugin-dir /absolute/checkout/plugins/ohmyorch`. This flag loads code for that session without hard-coding a machine path into project settings. The public catalog is published from this repository with plugin version 0.0.1. Public packaged artifacts remain subject to the recorded license and live-test gates. Never enable legacy hooks and plugin hooks together.

Read [the architecture plan](docs/plan/CLAUDE-CODE-PLUGIN-MIGRATION.md), [implementation evidence](docs/plan/PLUGIN-IMPLEMENTATION.md) and [the shared contract](plugins/ohmyorch/references/contract.md) before changing architecture. The plans retain explicitly historical baseline inventories; the current definitions live under `plugins/ohmyorch/`. The main session coordinates; analyst/specifier/ingestor/planner return authored handoffs; implementer owns product code and selected tasks; reviewer/tester persist their own selected verdict. Preserve independent evidence, seven gates, four completion conditions, derived resumption and verdict history. Do not silently strengthen preserved partial/UNVERIFIED acceptance or verification-text classification.

Resolve code from its installed location and consumer data from an explicit canonical project root. The source entry point is [plugins/ohmyorch/bin/ohmyorch](plugins/ohmyorch/bin/ohmyorch); invoke the installed equivalent as `"<plugin-root>/bin/ohmyorch" --project-root /absolute/project <operation>`, replacing the placeholder with its actual path. Configuration is created in the consumer at `.claude/ohmyorch/project.json`; runtime/backups/local approvals are ignored. Consumer files are data, never sourced. Bootstrap, adaptation, upgrades, reset and legacy migration are explicit previewable transactions. Never overwrite unowned intent, host scripts or edited managed guidance. Secrets and local provider settings are user-owned and outside inventories and packages.

Maintain Bash 3.2 and jq >=1.6 compatibility. Runtime Python/Node dependencies are prohibited; root npm/Python tooling is development-only. Use structured JSON parsing and stdout protocols, stderr for hook diagnostics, fail closed on missing activated validators, and no-op inactive hooks. Role hooks live in the plugin root dispatcher because plugin agent frontmatter hooks are ignored.

Validate relevant changes with `npm run check` and `npm test`. `npm run check` validates the plugin, documentation links/fragments and generated guide. For catalog/runtime/release changes also run `npm run test:marketplace`, both strict Claude plugin/catalog validators, and allowlisted development packaging. Every claimed live compatibility result needs actual authenticated evidence. Live delegated-agent and full-lifecycle tests remain gates for public packaged artifacts and support claims. A synthetic payload test is not a live identity test. Do not mark [release readiness](docs/plan/plugin-release-readiness.json) fields true without evidence or invent the owner's distribution license. The artifact workflow reports pending evidence and skips public packaging/upload; the CLI public-package gate still refuses missing evidence.

The authoritative product version is [the plugin manifest](plugins/ohmyorch/.claude-plugin/plugin.json), currently `0.0.1`. Release tags match the manifest version exactly, without a `v` prefix. The owner explicitly authorized the one-time history reset and replacement of old tags with `0.0.1`; ordinary future releases remain immutable. Keep root package/lockfile versions, changelog, readiness version, guides and generated HTML consistent. Dependency, project-schema and historical copier versions have their own meaning. Marketplace update fixtures derive a newer patch version; do not turn an update test into a same-version reinstall. See [distribution and maintenance](docs/distribution.md) for install, update and recovery commands.

Never publish a tag or release as part of routine local validation. This publisher checkout has no consumer PRD/SPECS/OpenSpec scaffolding; neutral scaffolds live in plugin templates. A consumer's PRD/SPECS/CODEBASE and OpenSpec records remain project-owned. Active architecture/implementation plans and release-readiness JSON are maintainer records, not runtime definitions.

Keep `docs/OhMyOrch.md` as the visual guide's source. Run `npm run docs:build` after editing it; `npm run check` rejects stale generated HTML. README displays the published `docs/images/OhMyOrch.png` logo immediately after its title, followed by the hosted guide URL; the Markdown guide and generated HTML retain the same logo. Maintain the SVG flows and imported slides beside that preserved image. Pages publishes only the entry-point redirect, guide HTML and its local assets. This website uses local images/CSS/JS; the plugin's self-contained HTML output contract is tested against dedicated fixtures instead of the public site.

Keep local links relative to the file that contains them and check fragments against the target's actual headings/IDs. Pages omits Markdown and plugin source, so the renderer maps repository-source links to GitHub. Link current instructions to existing source files; label consumer paths, neutral-template placeholders and retired historical paths explicitly. Historical audit paths and `references/legacy-files.json` fingerprints must not be mistaken for current executables or deleted from the migration contract. Deliberately invalid test fixtures are not public documentation. Recheck external URLs when changing cited guidance; a redirect is acceptable only when it still supports the linked claim.
